# Session End — DJ discovery split, centralized DB, full provenance

Branch: main (all changes uncommitted)

## What this session did

Started as "break up the DJ Set Discoveries playlist into subgenres". Became a
data-integrity job once it turned out the playlists were short because most of
the library never reached them.

### 1. Subgenre playlists — wrong source, twice
- First build used the WHOLE library (12,854 tracks). Deep House got 1,982.
- Second attempt used the Spotify playlist snapshot — also wrong: it is a lossy
  subset. `library.db` knows 5,093 DJ-set tracks; the playlist held 2,279.
- Final: `--source dj-sets` (default) reads `dj_set_tracks`. 51 playlists.

### 2. Coverage: 34% -> 66%
```
5,093  DJ-set tracks
4,386  classified      (was 3,912)
3,174  have a subgenre (was 2,839)
3,379  on a playlist   (was 1,755)
```
Four leaks closed:
| leak | fix | recovered |
|---|---|---|
| Last.fm had no tags (1,184) | `refetch_missing_tags.py` w/ normalised names | 475 |
| no reachable Spotify ID (809) | `resolve_synthetic_ids.py` | 802 |
| stuck at parent genre (1,073) | `--level genre` catch-alls | 594 |
| under `--min-tracks 10` | threshold now counts post-resolution | 67 |

### 3. Root causes fixed (not just patched)
- **Scraper concatenates features**: `Disclosureft. Eliza Doolittle`.
- **Last.fm does not autocorrect diacritics**: `RÜFÜS DU SOL` -> 0 tags,
  `Rufus Du Sol` -> tags. This was the bigger of the two.
- **HTML leaking into fields** (1 row): `strip_markup()` guards the boundary.
- `dj_ingest.py` now normalises AT INGEST. `dj_set_tracks` carries raw_artist/
  raw_title (audit trail, never rewritten) plus artist/title (normalised).
  **3,210 of 6,940 rows (46%) differed.**
- `dj_stub_tracks`, `backfill_missing_tracks`, `lastfm_tags.promote_orphans`
  all read `COALESCE(artist, raw_artist)` so bad names stop propagating.

### 4. One database
Pipeline state lived in JSON files beside library.db, written by six scripts
with no single owner:
- `spotify_cache.json` -> `spotify_id_cache` (NULL id = known miss)
- `spotify_search_misses.json` -> same table
- `discovery_playlist_ids.json` -> `playlist_snapshots` / `playlist_tracks`

`_load_spotify_cache()` still returns a dict-like, so no call site changed, but
assignment writes through to the DB immediately — that is what makes a mid-run
ban non-destructive. `_save_spotify_cache()` is now a no-op.
Retired files: `archive/json-sidecars-retired-20260825/`.

### 5. Provenance + playlist membership
- `playlists` (842) + `playlist_tracks` (19,541) — which songs are in what.
- `track_provenance` VIEW (21,518 rows) — one row per (track, origin) with
  dj / set / date / position / how-it-was-spelled. `track_sources` collapses to
  one row per DJ; the view keeps the detail.
- **3,144 tracks had no origin recorded** though `dj_set_tracks` knew it.
  `backfill_provenance.py` recovered 3,143. One mojibake track remains.
- `track_story.py "<query>"` prints metadata + every set + every playlist.

## Bugs found and fixed
1. Playlist items nest under `item`, not `track`. `fields="items.track.id"`
   returned `{}` per entry -> empty dedupe set -> every rebuild re-added
   everything. Same defect in main.py, festival_playlist.py, sessions.py
   (there it made "clear" a no-op).
2. `_get_or_create_playlist` paged all playlists per call (~2,450 requests).
   Now indexed once per process.
3. Unbounded 429 backoff would have slept 23h. Capped at 120s.
4. `.title()` mangled acronyms ("Uk Garage").
5. `promote_orphans()` only handles `spotify_id IS NULL`, so 668 tracks with
   real IDs but no `tracks` row were invisible.
6. `--min-tracks` counted DB rows, not tracks that resolve to a Spotify ID.
7. `resolve_synthetic_ids.py` crashed on a transient 502 — now retries 5xx,
   still aborts instantly on 429.
8. Spotify moved playlist size from `tracks.total` to `items.total`.

## Spotify quota — the binding constraint
Two 24h `QUOTA_EXCEEDED` bans this session. The daily budget is shared across
endpoints but lifts per-endpoint (reads came back ~9h before search did).
Two full playlist syncs + ~700 searches is enough to exhaust it.
Guardrails: `MAX_RETRY_AFTER=120`, abort-not-sleep, write-through cache.

## Open items
- **709 tracks have no Last.fm tags** even after normalisation; **938** sit at a
  parent genre. Not retryable — needs Discogs / Beatport / Spotify artist genres.
- `artist_genres` table is empty (0 rows), never populated.
- Audio features unavailable: Spotify 403s that endpoint for this app.
- 3 playlists (Footwork, Neo-Soul, Funk Carioca) were in the "leave alone" 15
  but crossed the threshold after recovery and got converted to real discovery
  playlists. User may want these reverted.
- Nothing committed. Working tree on `main`.

## Addendum — rate-limit hardening (same session)
Third ban hit while testing. Fixed properly rather than by being careful:
1. `spotify_budget.py` — daily ceiling persisted in `spotify_api_usage`,
   enforced in `_spotify_call` (the single chokepoint). In-memory counting with
   a lock-tolerant flush, since accounting must not break the work.
2. A 429 with a long Retry-After records `cooldown_until`; later runs refuse
   before calling. Re-running during a ban now costs 0 requests, not 1/attempt.
   `@guard` on each entry point turns it into a message, not a traceback.
3. `playlists.snapshot_id` (free, arrives in the catalogue page) skips
   membership reads for unchanged playlists; playlist index comes from the DB
   instead of 17 API pages per process.
Steady-state cycle ~440 requests -> ~40. Cooldown active until 2026-08-27T16:58.

## Addendum 2 — the guard was not actually global
Audit found `_spotify_call` covered only the scripts I had touched:
- ~90 direct `sp.foo()` calls across 19 files bypassed the budget
- 8 scripts construct their own `spotipy.Spotify()` and never import `auth`

Fix: `spotify_guard.py` patches `spotipy.Spotify._internal_call` — the single
HTTP chokepoint, applied at class level so every instance is governed.
`check_budget_guard.py` enforces the import. Removed the now-double charge in
`_spotify_call`. Budget ceiling now learns from `requests_at_ban`.

### Pagination bug (worse than the quota issue)
All paginators broke on `len(items) < page_size`. Spotify returns 49-item pages
mid-listing, so reads silently truncated: the catalogue saw 547 of 1,546
playlists. Consequences: an existing playlist looks absent -> duplicate created;
`playlist_existing_ids` returns a partial set -> tracks double-added. That is
the same class of bug as the original `items.track.id` defect.
Fixed in tracklist_scraper, main, sessions, pull_library, slot_add, aggregate_italo.

Measured after: sync_playlists 287 -> 11 requests, build --sync ~130 -> 12.
